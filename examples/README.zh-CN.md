# LifeOS Examples / 端到端示例

[English](./README.md) | **简体中文**

这些示例用于验证 LifeOS v0.1 是否真的能够从真实情境走到行动与复盘，而不是只停留在概念层。

## 示例 1：我不知道该不该换工作

### Situation
当前工作稳定，但成长变慢；外部有一个收入更高、风险也更大的机会。

### Runtime
```text
Clarify → Self → Context → Goal → Thinking → Decision → Next Action
```

### Facts / Assumptions / Unknowns
- Fact：当前岗位稳定。
- Fact：外部机会收入更高。
- Assumption：新岗位一定能带来更快成长。
- Unknown：新团队管理质量、长期业务稳定性。

### Decision Focus
不是简单比较工资，而是明确：当前阶段真正优化的是稳定、成长、收入、家庭时间还是长期职业资本。

### Next Action
在做最终选择前，针对最大未知项完成一次定向信息验证，例如与未来直属负责人确认团队目标、成功标准和 12 个月业务风险。

### Checkpoint
拿到关键未知信息后重新运行 Decision System。

## 示例 2：突然接手一个陌生项目

### Situation
原负责人离开，需要快速接手一个领域陌生、风险较高的项目。

### Runtime
```text
Role → Context → Thinking → Learning → Communication → Execution
```

### First Questions
1. 项目真正的 Outcome 和成功标准是什么？
2. 当前状态与计划差多少？
3. 最大三个风险是什么？
4. 谁掌握关键信息？
5. 哪些决定只有我能做？

### Next Action
先形成一页 Project Situation Map，而不是立即重做完整项目计划：Outcome、Milestone、Stakeholders、Current State、Top Risks、Unknowns、Next Checkpoint。

## 示例 3：一次重要项目失败

### Situation
项目延期并最终没有达到预期效果，团队情绪较差。

### Runtime
```text
Emotion & Energy → Review → Thinking → Learning → Execution
```

### Review
```text
Expected: 按计划上线并达到目标指标
Actual: 延期，上线后效果低于预期
Gap: 时间 + 结果双重偏差
```

进一步区分：
- Decision Quality：当时是否基于合理信息做决定？
- Execution Quality：执行过程中有哪些可控问题？
- Luck / External：哪些结果来自不可控变化？

### Lesson Rule
不要写“以后加强沟通”这种无法验证的总结。应形成行为变化，例如：

> 对高风险依赖，在开发启动前必须完成 owner、deadline、fallback 和 checkpoint 四项确认。

### Next Action
把该规则加入后续项目 Playbook，并在下一项目第一个 checkpoint 验证。

## 验证标准

LifeOS v0.1 的示例应该证明：

```text
真实问题
   ↓
结构化理解
   ↓
适当的 Core OS 路由
   ↓
具体下一步行动
   ↓
真实结果
   ↓
可验证的 Lesson / Model Update
```
